# 制品元数据熔断网关 + 依赖锁定

部署系统读取制品元数据时，上游故障会引发密集重试。本项目是一个 **FastAPI + SQLite
的双 worker 熔断网关**：按制品名把 `GET` 查询转发给本地目录服务，慢查询不会阻塞其他
查询，两个 worker 进程共享同一份熔断状态，重启后状态仍然保留。

在此之上新增**依赖锁定页（`/lock`）**：发布工程师输入根制品与允许版本，系统在版本化
目录中递归求解出一份**相容的安装清单**（每个制品仅选一个版本，含 SHA-256、摘要与目录
修订）；找不到相容组合时明确给出**无解**，而元数据经熔断查询不可用时给出与无解区分的
**查询失败**。

打开 <http://localhost:8000/> 使用熔断页，打开 <http://localhost:8000/lock> 使用依赖
锁定页。

## 快速启动

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000/
```

需要 Docker 与 Docker Compose v2。Compose 会构建两个服务：

| 服务 | 说明 | 端口 |
| --- | --- | --- |
| `upstream` | 示例本地目录服务，提供 `/artifacts/{name}`（旧）与 `?version=` 版本化查询、模式控制与访问计数 | 仅集群内 9000 |
| `gateway` | 熔断网关 + 依赖锁定，`uvicorn --workers 2`，SQLite 位于命名卷 `breaker-data` | 宿主机 8000 |

`gateway` 使用命名卷挂载 `/data`，容器重启或重建后熔断状态与目录修订仍在。镜像内置
首版目录（`seed_data.py`），数据库首次启动时由单个写事务原子播种，双 worker 并发启动
也只会产生修订 1。

### 不使用 Docker 的本地运行

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
export UPSTREAM_URL=http://127.0.0.1:9000 GATEWAY_DB=./data/breaker.db
python -m uvicorn upstream:app --port 9000 &
python -m uvicorn app:app --port 8000 --workers 2
```

## 熔断语义

状态按**制品名**独立维护，存放在 SQLite（WAL、写事务 `BEGIN IMMEDIATE`），因此对两个
worker 进程共享，并对重启持久。

* **CLOSED**：转发请求。失败（连接失败 / 超时 / 5xx）按**完成顺序**连续计数；
  其它响应（2xx/3xx/4xx）把计数清零。连续第 3 次失败立即熔断。
* **OPEN**：所有请求直接返回 **503**（带 `Retry-After`），**不访问上游**。
  冷却 **2 秒**后，恰好一个请求通过原子 CAS 成为唯一的**恢复探测**；其余请求继续 503。
* **HALF_OPEN**：只有一个探测在飞。探测成功 → CLOSED 并清零；探测失败或超时 →
  重新 OPEN 并重新计算 2 秒冷却。探测进程崩溃后，探测槽位在租约到期 / 重启时释放，
  可以再次探测。
* 每次调用总时长上限 **1 秒**（`asyncio.wait_for`），连接、读取、解析合计计算。

### 旧结果不会覆盖新结论

* 准入时记录该次调用所属的 **epoch**。若调用期间熔断已打开（epoch 变化），这次结果
  被视为过期：**熔断前发出、熔断后才成功的慢请求既不会清零失败数，也不会让熔断恢复**
  （响应中标记 `stale_success_ignored`）。
* 探测结果携带 **probe generation**。旧代次探测迟到时被丢弃（`stale_probe_ignored`），
  不会覆盖新代次的判定。
* 探测者进程退出后，`HALF_OPEN` 记录被识别为无主，冷却结束后可再次探测。

### 并发与阻塞

* 每个 worker 是独立的 asyncio 事件循环，上游调用全程异步；慢查询不会阻塞同 worker
  内的其他查询。
* 上游 HTTP 连接在进程内复用连接池。
* SQLite 写事务放在线程池执行；常态放行与熔断拒绝都是只读快路径，不占用写锁。

## HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/meta/{artifact}` | 经熔断器查询元数据。成功 200，上游失败 502，熔断 503 |
| GET | `/api/breakers` | 所有制品的熔断状态、最近事件、转发计数 |
| POST | `/api/reset` | 清空熔断状态与计数（演示用） |
| GET/POST | `/api/upstream-mode` | 读取 / 设置示例上游模式：`normal`、`delay`、`503`，可带 `delay` 秒数 |
| GET | `/api/upstream-stats` | 上游实际收到的 `/artifacts` 请求数（地面真值） |
| POST | `/api/upstream-stats/reset` | 清零上游计数 |
| GET | `/lock` | 依赖锁定网页（目录替换、求解、查看清单/失败原因） |
| GET | `/api/lock/revisions` | 列出全部保留的目录修订与当前修订 |
| GET | `/api/lock/catalog?revision=N` | 读取某修订目录（缺省为当前修订） |
| POST | `/api/lock/catalog` | 整版替换目录；先校验后单事务写入，失败不改原目录，成功追加新修订 |
| POST | `/api/lock/solve` | 固定开始时修订并求解，返回 `sat` / `unsat` / `query_failed` |
| GET | `/api/lock/sample-catalog/v2` | 内置换版样例目录（仅供编辑，不写入，需显式替换才生效） |
| GET | `/healthz` | 健康检查 |

说明：`/api/meta` 的 4xx（例如制品不存在）视为上游**健康**响应，原样返回并清零计数；
仅连接失败、超时和 5xx 计入熔断失败。旧的熔断接口与查询路径保持不变，锁定功能只是
在同一状态机上新增了版本化查询入口。

## 依赖锁定语义

### 目录模型与限制

* 一份目录最多 **12 件制品**、每件最多 **4 个版本**；每个版本带 **SHA-256** 与若干
  依赖，每个依赖给出**允许版本集合**。版本一律按**字符串精确匹配**，不做范围解析。
* 递归依赖中**同名制品只能选定一个版本**；出现**依赖环不直接判错**——指向已选定制品
  的环边只做一次版本约束校验。
* 替换是**整版替换**：文档先完整校验（结构、数量上限、SHA-256 形状、重复名/版本等），
  通过后在单个 `BEGIN IMMEDIATE` 事务中追加新修订；**无效目录或写入失败不会改动当前
  目录**。每次成功替换都新增一个修订，**旧修订全部保留可读**。

### 求解：完整回溯，而非贪心

求解器对候选版本做**完整时序回溯 + MRV（最受限变量优先）分支**：贪心先选的版本走入
死胡同时会回退并尝试其余版本，只有**穷尽整个搜索空间**后才报告无解，因此不会因贪心
选版失败而误报无解。结果带搜索统计（节点数、回溯次数、剪枝次数）。

### 修订固定（求解期间换版）

每次 `solve` 在**开始时**读取当前修订并固定其快照（修订 id 与文档摘要随结果返回）。
求解过程中即使目录被替换，本次求解仍只依据开始时的修订；**后续**求解才会读到新修订，
不会把新旧版本混入同一份清单。

### 三种结果，失败模式互不混淆

| 结果 | 含义 |
| --- | --- |
| `sat` | 找到完整相容组合，且每个版本的元数据经熔断查询并通过 SHA-256 校验 |
| `unsat` | 目录约束下**不存在**相容组合（附人类可读原因：无可用版本、缺失制品、版本冲突等） |
| `query_failed` | 约束层面**已找到**完整组合，但元数据经熔断查询失败（熔断打开 / 5xx / 超时 / 404 / 摘要不一致） |

元数据查询复用原有熔断器：先 `admit` 再调用上游，熔断打开直接记为 `query_failed`，
与 `unsat` 严格区分。摘要校验会剔除目录服务注入的传输字段（`artifact`、`source_file`、
`source_mtime`），只对版本元数据本体计算 SHA-256，并同时比对「目录声明值」「上游返回
值」与「本地重算值」。

### 安装清单内容

`sat` 清单按从根制品出发的 BFS 顺序列出，每项包含：制品名、**选定版本**、目录声明与
上游返回的 **SHA-256**、校验结论、元数据**摘要**（group/packaging/license/size 等）、
直接依赖，以及整份清单依据的**目录修订 id 与文档摘要**。

### 内置样例

种子目录（修订 1，由 `build_seed.py` 生成，源数据在 `versioned_artifacts/v1`）覆盖：

* **菱形 + 贪心陷阱**：根 `example-app` 允许 `2.0.0`。目录把 `http-client 3.1.0` 排在
  `3.0.0` 前，但 3.1.0 要求 `json-codec 2.0.0`，而 `core 2.0.0` 钉死 `json-codec 1.4.0`。
  贪心先选 3.1.0 会死路；回溯到 3.0.0 才能得到完整清单（响应中 `backtracks >= 1`）。
* **循环依赖**：根 `plugin-a` 允许 `1.0.0`，与 `legacy-config 0.9.0` 互相依赖，环不报错。
* **无解**：根 `example-app` 允许目录中不存在的 `9.9.9`，返回 `unsat` 及原因。
* **换版样例**：`/api/lock/sample-catalog/v2`（源数据 `versioned_artifacts/v2`）。替换后
  形成修订 2，多个版本与 SHA-256 变化；此时上游仍挂载 v1 元数据树，对修订 2 求解会得到
  `query_failed`（`digest_mismatch` / 404），直观展示换版与查询失败的区别。

### 建议的手动验证（依赖锁定）

1. 打开 `/lock`，点击「菱形 + 贪心陷阱（回溯成功）」：得到 `sat` 清单，搜索统计显示
   发生过回溯，且所有条目 SHA-256 校验一致、清单标注目录修订。
2. 点击「无解样例」：得到 `unsat` 与具体原因，而非查询失败。
3. 在熔断页把上游切到 **503** 并连点三次制造熔断，再回 `/lock` 求解：得到
   `query_failed`（含 `circuit_open`/`upstream_failure`），证明与无解区分。
4. 「载入换版样例目录 v2」→「校验并替换目录」：产生新修订、旧修订仍在；再次求解会固定
   到新修订。点「制造一个无效目录」后替换，应被 400 拒绝且当前修订不变。
5. 求解进行中替换目录（可先把上游切到延迟模式放大窗口）：进行中的求解保持开始修订，
   之后的求解才使用新修订。

## 建议的手动验证

1. 将上游切到 **503**，连续查询同一制品 3 次：前两次 502，第三次之后变 503（熔断）。
   再查几次，观察「上游实际访问次数」不再增长。
2. 把上游切回**正常**，等待 2 秒后查询：该请求作为“恢复探测”成功，熔断恢复。
3. 切到**延迟**并设置为 `0.8`，用“并发请求数”发起多次查询：全部在 1 秒内成功，
   说明慢查询之间互不阻塞；把延迟设为 `3` 则每次查询约 1 秒超时并计为失败。
4. 熔断后在浏览器刷新页面，或 `docker compose restart gateway`：熔断状态仍为 open。

## 自动化测试

```bash
pip install -r requirements-dev.txt
# 需要先启动 gateway 与 upstream（Compose 或本机进程）
GATEWAY=http://127.0.0.1:8000 python -m pytest -q tests/
```

* `tests/test_unit.py`：直接驱动状态机，覆盖失败计数/清零、熔断、单探测选举、
  探测失败重冷却、慢成功不能恢复、旧探测代次不能覆盖、无主探测释放、超时与错误分类。
* `tests/test_breaker.py`：通过 HTTP 覆盖真实双 worker 行为，包括两个 worker 都被用到、
  超时上限、并发探测只放行一个、慢查询并发、以及（设置 `GATEWAY_RESTART_CMD` 时）
  重启后状态保留。
* `tests/test_locker_unit.py`：目录校验上限、原子替换与旧修订保留、双 worker 并发播种
  只产生一个修订、完整回溯（贪心陷阱）、菱形单版本约束、环不判错、真无解穷尽搜索、
  摘要校验与传输字段剥离、查询失败与无解区分。
* `tests/test_locker_http.py`：经 HTTP 端到端覆盖锁定流程，包括菱形回溯出完整清单、
  环可解、无解返回 `unsat`、无效替换被拒且当前修订不变、成功替换追加修订并保留旧修订、
  求解期间换版不污染进行中的求解、熔断打开导致 `query_failed` 而非 `unsat`、旧
  `/api/meta` 接口行为不变。
